# Milestone 4 — the Noctrowl export pipeline: design

## Scope recap

This milestone builds a one-way, manual-trigger, incremental file handoff
from Project-Alakazam's Postgres database to Project-Noctrowl, via a CSV
file uploaded to a new, separate Google Drive folder. Per CLAUDE.md's
"Milestone 4 decisions, confirmed 2026-09-10":

- Alakazam's own, separate Google Cloud OAuth client/token (never
  Noctrowl's).
- A new, separate top-level Drive root for Alakazam (not filed under
  Noctrowl's "Finance & Accounting" tree).
- Manual trigger, incremental: a callable script/function, no in-app
  button required. Exports only purchases saved since the last successful
  export, tracked via a new `purchases.exported_at` column.

Explicitly out of scope: any importer/parser on Noctrowl's side (CLAUDE.md:
"nothing automated in this build — no importer/parser is being built on
Noctrowl's side as part of this plan"), any change to how Milestone 2/3
compute or store purchase data, sale/depletion/eBay/consignment/pre-order
logic, and an in-app "Sync Now" button (optional, not built).

## Why the CSV shape here supersedes the original plan draft

An earlier planning document assumed a single `allocation_method` column
per line. That's stale: Milestone 1's redesign made item cost and shipping
fully independent (direct-entry-by-default item pricing with a narrow
lump-sum opt-in, and three separate, mutually-exclusive shipping modes —
see CLAUDE.md's Milestone 1 summary and `migrations/001_initial_schema.sql`).
There is no single "allocation method" per line anymore — a line has an
independent pricing mode (`direct` / `lumpsum_group`) and an independent,
effective shipping-costing method (`none` / `manual` / `pooled`, itself
possibly overridden per-line via `ships_separately`). This design reflects
the real schema, not the stale draft.

## Drive destination

**A new, separate top-level Drive root**, a single folder:

```
Alakazam Inventory Exports/
├── alakazam-export-20260910T140000Z.csv
├── alakazam-export-20260915T090000Z.csv
└── ...
```

Justification: unlike Noctrowl's four document types uploaded in monthly
batches (eBay sales, Payoneer, bank statements, invoices — see Noctrowl's
CLAUDE.md), this is a single incremental CSV type, generated by
Alakazam itself (not a human uploading a scanned document), triggered
manually and irregularly. Noctrowl's Year → Month folder hierarchy exists
to keep a *human-browsable* monthly-batch record of raw uploads; there is
no equivalent need here. A flat folder — one timestamped file per run —
is simpler, sufficient, and still fully browsable/orderable by filename.
If export volume/frequency ever grows enough that a flat folder becomes
unwieldy, light date-based subfolders (e.g. by year) can be added later
without breaking anything already exported — the folder-finding logic
(`find_or_create_folder`) doesn't assume flatness structurally.

The folder is found-or-created idempotently by name on every run
(`export/runner.py` via `export/drive_client.py::find_or_create_folder`),
directly under "My Drive" of whichever Google account completes the OAuth
consent flow (`scripts/authorize_google_drive.py`) — that account's own
storage quota, same as Noctrowl's own OAuth path (see Noctrowl's
`ingestion/drive_client.py` module docstring for why OAuth, not a service
account, is required for a write path on a personal Gmail Drive).

## CSV column shape

One row per **costed unit**: a serialized unit gets its own row; a
fungible line gets exactly one row (it has no individually-identified
units to split across). Column order, left to right:

| Column | Source | Notes |
|---|---|---|
| `purchase_id` | `purchases.id` | DB id, for exact traceability |
| `purchase_line_item_id` | `purchase_line_items.id` | DB id |
| `serial_unit_id` | `serial_units.id` | DB id; empty for fungible rows |
| `purchase_ref` | `purchases.purchase_ref` | e.g. `PUR-2026-0102` |
| `purchase_date` | `purchases.purchase_date` | ISO-8601 (`YYYY-MM-DD`) — the booking/payment date, matching this system's "books at time of payment" convention |
| `vendor_description` | `purchases.vendor_description` | free-text vendor/description, for human audit trail |
| `item_id` | `items.id` | DB id |
| `sku` | `items.sku` | |
| `item_name` | `items.name` | |
| `category` | `categories.name` | **literal string value** — `TCG` / `Watches` / `Automotive` / `Toys & Collectibles` / `Others`, matching Noctrowl's own category labels exactly (`inventory/seed.py`'s `CONFIRMED_CATEGORIES` display names) |
| `identity_mode` | `items.identity_mode` | `fungible` / `serialized` |
| `serial_identifier` | `serial_units.serial_id` | empty for fungible rows |
| `quantity` | `purchase_line_items.quantity` for fungible rows; always `1` for serialized rows | See "Why quantity is always 1 for a serialized row" below |
| `pricing_mode` | `purchase_line_items.pricing_mode` | `direct` / `lumpsum_group` — how the line's *item cost* was priced |
| `shipping_costing_method` | derived, see below | `none` / `manual` / `pooled` — how THIS LINE's shipping was actually costed |
| `allocated_item_cost` | `purchase_line_items.allocated_item_cost` | **verbatim, line-level** — see "Why the three core money columns are always line-level" below |
| `shipping_share` | `purchase_line_items.shipping_share` | verbatim, line-level |
| `line_total` | `purchase_line_items.line_total` | verbatim, line-level |
| `unit_cost` | computed convenience field, see below | the one place a real per-row number is derived |
| `currency` | `purchases.currency` | `IDR` for every real/test purchase today; groundwork for future non-IDR |
| `fx_rate_to_idr` | `purchases.fx_rate_to_idr` | nullable; empty string in CSV when null |

CSV mechanics: UTF-8, RFC 4180 (Python `csv` module defaults, CRLF line
endings), header row always present, money columns written as plain
decimal strings (e.g. `"11540000"`, never a float/scientific notation),
nulls rendered as empty string (CSV has no native null).

### Why the three core money columns are always line-level

`allocated_item_cost`, `shipping_share`, and `line_total` are "already
computed and stored by the Milestone 2 engine" per the brief — this design
takes that literally: these three columns are always exact, unmodified
reads of `purchase_line_items`' own stored columns of the same name, for
**every** row, fungible or serialized. This is a deliberate choice, not an
oversight: the schema has no per-unit breakdown of item-cost-vs-shipping to
read for a serialized line instead (`split_serial_unit_costs` in
`inventory/allocation.py` splits the LINE's already-combined `line_total`
evenly across units — the combined total per unit is stored on
`serial_units.acquired_cost`, but the item-cost/shipping split that
produced that combined total is not separately preserved per unit anywhere
in the schema). Rather than inventing a per-unit split that isn't real data
(which would violate "don't recompute"), these three columns intentionally
repeat the same line-level values across every unit-row of a serialized
line — clearly line-level facts, not per-unit ones. A reader who sums
`line_total` grouped by DISTINCT `purchase_line_item_id` recovers the exact
purchase-level reconciliation total; naively summing every row's
`line_total` would double/N-count a multi-unit serialized line, which is
exactly why `purchase_line_item_id` is included as an explicit column —
so any downstream consumer can de-duplicate correctly rather than guessing.

### The one computed field: `unit_cost`

This is the one column genuinely computed per row, not read verbatim:

- **Fungible row**: `unit_cost = line_total / quantity` (unrounded Decimal
  division — the same convention already used by
  `inventory/queries.py::get_fungible_purchase_rows`'s
  `allocated_unit_cost`, reused here rather than inventing a second
  rounding rule).
- **Serialized row**: `unit_cost = serial_units.acquired_cost` for that
  specific unit — this is NOT computed at all, it's a direct, already-
  stored read; "computed" only in the trivial sense that it varies by row.
  This is the one place a genuine per-unit cost figure surfaces in the
  export, which is the whole reason "one row per costed unit" was
  specified for serialized items.

### Why `quantity` is always `1` for a serialized row

Each serialized row represents exactly one physical unit. Setting
`quantity = 1` (rather than, say, the line's total quantity, or leaving it
blank) means `SUM(quantity)` for a given SKU across the whole export
always equals the true total unit count for that SKU, regardless of
whether it's fungible or serialized — a useful, honest invariant for any
downstream reconciliation, achieved without recomputing anything.

### `shipping_costing_method`: a genuinely per-line derivation, not a blind copy

A purchase's `shipping_mode` header field (`none`/`manual`/`pooled`) does
NOT always describe every one of its lines: a line inside a `pooled`
purchase can opt out via `ships_separately` and get its own
`manual_shipping_amount` instead
(`inventory/allocation.py::compute_purchase_allocation`). This column
reports the EFFECTIVE method for that specific line:

```
if purchase.shipping_mode == "pooled" and line.ships_separately:
    "manual"
else:
    purchase.shipping_mode
```

This reads two already-stored boolean/string flags and applies a trivial
mapping — it is not a recomputation of any money value, only of which
descriptive label correctly applies to this row. Getting this wrong would
mislead an auditor into believing a line's shipping was pooled when it was
actually priced independently.

## Incremental export mechanism

`migrations/002_add_purchases_exported_at.sql` adds a nullable
`purchases.exported_at TIMESTAMPTZ` column (plus a supporting index).
`NULL` means "never successfully exported." `export/runner.py::run_export`:

1. Queries `SELECT id FROM purchases WHERE exported_at IS NULL ORDER BY id`.
2. If empty, returns immediately — makes **zero** Drive API calls (no
   pointless empty-file upload or folder-creation call for a no-op run).
3. Otherwise builds the CSV for exactly those purchase ids
   (`export/csv_builder.py::build_export_csv`), uploads it to the
   found-or-created export folder, and — **only if both Drive calls
   return successfully** — marks every one of those purchase ids'
   `exported_at` to the run's timestamp, in the same DB transaction the
   caller controls.
4. Any exception from the Drive client (folder lookup/creation, or the
   upload itself) propagates unchanged, and `exported_at` is never touched
   for any row in that run — mirrors Noctrowl's own posted-row-tracking
   discipline ("never silently lose or double-send data"): a failed run
   leaves every affected purchase exactly as eligible for the next run as
   it was before this one started. There's no partial-credit state (some
   rows marked, others not, from one run) — the whole batch either
   succeeds together or is retried together.

`run_export` never commits/rolls back the connection it's given (same
convention as `inventory/purchases.py::save_purchase`) — `scripts/
run_export.py` (the CLI wrapper) owns the transaction via
`engine.begin()`, so a raised exception naturally rolls back any partial
work (including the `exported_at` update, if it somehow got that far)
before propagating.

## What's explicitly NOT built this milestone

- No importer/parser on Noctrowl's side — the CSV lands in Drive and stops
  there, from this project's perspective.
- No in-app "Sync Now" button (an optional nice-to-have per the brief, not
  required — skipped to keep scope tight; `scripts/run_export.py` is the
  callable entry point, same shape as Noctrowl's own Milestone 3 boundary).
- No change to `inventory/allocation.py`, `inventory/purchases.py`, or the
  Milestone 2/3 schema beyond the additive `exported_at` column.
- No real OAuth credentials — those require a human to create a Google
  Cloud project and OAuth Client ID and run
  `scripts/authorize_google_drive.py` once, locally. See the milestone
  report for the exact remaining setup steps.
