# Project-Alakazam

## What this is
Inventory management system for the same multi-category eBay reselling business as **Project-Noctrowl** (the sibling bookkeeping/accounting project at `../project-noctrowl-2`). This document is a knowledge-transfer seed, written by Main-agent from Project-Noctrowl's session on 2026-09-09, so this project's build starts aligned with the accounting system rather than drifting from it and needing reconciliation later. It captures what the accounting side already knows, expects, and has deliberately left open for an inventory system to eventually fill in.

**This file does not prescribe Project-Alakazam's own architecture, schema, or tech stack.** Those are for the user and this project's own build agent to decide. What follows is business context and integration constraints only — the same categories, the same identifiers, the same real vendor/business facts already confirmed on the accounting side, so the two systems can eventually talk to each other without a translation layer.

## Why this project exists, in Project-Noctrowl's own words
Project-Noctrowl's CLAUDE.md has carried this note since 2026-09-01:

> Cost-to-transaction traceability (manually linking a purchase's cost, including shipping, to the specific sale it belongs to) is deliberately deferred to very late development, **built together with a genuine inventory system**, once all current build milestones are complete — not speculatively before then. This is safe to defer: the data these features would eventually reference (individual invoice records, per-transaction journal entries, `ebay_order_ref` on sale lines) is already being preserved by the current milestones, so nothing about building milestones first forecloses adding this later.

Project-Alakazam **is** that genuine inventory system. Its eventual job, from the accounting side's perspective: let Project-Noctrowl move from "COGS expensed in aggregate at time of purchase" to "COGS matched to the specific item that actually sold" — without either system needing to be rebuilt to make that connection.

As of 2026-09-09, this is not yet wired up. Project-Noctrowl's ledger still expenses COGS in aggregate at time of purchase. Nothing about that changes until this project (or a defined integration between the two) actually exists and the two sides agree on how to connect.

## Sales/ownership models this business runs — inventory needs to reflect the differences
Three models, sometimes within the same account, each implying a different inventory state:

1. **Stock model** — buys inventory up front, lists it, sells it later. Standard owned-inventory case: item is on-hand and owned by the business from acquisition until sale (or write-off).
2. **Pre-order/dropship model** — lists an item *before* owning it; only buys and ships it after it sells. Needs a distinct "sold but not yet acquired/fulfilled" state — this is not the same as normal on-hand stock, and COGS/acquisition happens *after* the sale event, not before.
3. **Consignment model** — items are owned by a third party (a consignor), physically held in the seller's warehouse, never the seller's own asset. On sale, the seller ships to the buyer, collects full payment, then reimburses the consignor (minus commission/fee) afterward. **The item is never inventory the business owns** — it needs to be tracked as held-but-not-owned, distinct from both of the above.

### Consignment specifics already established on the accounting side
- Consignment listings are identified by a **`CONSIGN-` SKU prefix** on the eBay listing. Anything without that prefix defaults to normal stock/pre-order treatment on the accounting side. If this project tracks consigned items separately, use the same `CONSIGN-` convention (or whatever supersedes it) so both systems agree on what's consigned without needing a manual cross-reference.
- The accounting side tracks the consignor payable liability as **one aggregate figure**, not per individual consignor — deliberately, because "a separate system (not [Project-Noctrowl]) will handle consignor-level relationship/operational tracking." That separate system is very plausibly this one. If Project-Alakazam becomes the place consignor-level detail (who owns what, what's owed to which consignor individually) actually lives, that's consistent with how Project-Noctrowl was designed — it was left deliberately shallow on this exact point, expecting something else to go deeper.
- Project-Noctrowl retains a bare consignor/item reference field on each consignment transaction specifically "so a future consignment system can reconcile against this ledger without re-architecting it" — written in anticipation of a project like this one. Preserve a compatible reference on this side too.
- Two consignor payout formulas currently run in parallel on the accounting side (a price-tiered rate table, and an experimental gross-minus-fees-minus-shipping model). Project-Alakazam doesn't need to compute payouts — that stays on the accounting side — but if this project ever surfaces "amount owed to consignor X," know that the real number depends on which of two live formulas applies to that specific transaction, decided manually per-sale on the accounting side (not a stored per-consignor/per-listing flag today).

## The real, practiced pattern for bundled purchases — worth designing around, not against
From Project-Noctrowl's CLAUDE.md (confirmed 2026-08-31): **the user already manually estimates per-transaction COGS today, informally, outside the formal books** — by allocating one bundled purchase's cost (often with shared shipping) across the multiple items it covers, by weight/value/estimate, not a fixed rule. This is real, current behavior, not a hypothetical edge case. If this project is meant to eventually produce a defensible per-item cost, it will very likely need to support "one purchase transaction, cost split across N items by some allocation method" as a first-class case, not an afterthought — that's already how the business actually operates, informally, today.

Key decisions from Milestone 1 that Milestone 2's schema/business-logic must implement faithfully (see `docs/design/ui-ux-design.md` for full detail, this is the summary that matters for the engine):

- **Item cost is direct-entry by default** — a line's price is entered as either "per unit" or "total for this line," with the other figure computed live; these are two views of one true value, not independently stored (a real bug was caught and fixed in the mockup where toggling between them silently corrupted the value instead of converting it — the engine must actually convert, never just reinterpret raw digits under a new label).
- **Lump-sum pricing is a narrow, explicit opt-in fallback**, not the default path — for the real, confirmed case where a bundle of items has one combined price with no per-item breakdown. Scoped to **one lump-sum group per purchase** (a line either joins it, split by Equal/By-Weight/By-Value, or is priced directly — no support for multiple simultaneous lump-sum groups in one purchase, a deliberate simplification).
- **Shipping cost is fully independent of item cost** — three mutually exclusive modes per purchase: **None**, **Manual** (exact amount per line), or **Pooled** (one shared total split Equally / By Weight / By Value — "By Value" reuses each line's already-computed item cost as its weight, not a separate value input). Any line can opt out of Pooled via "this item shipped separately" and get its own manual amount instead.
- **Reconciliation check**: sum of every line's (item cost, however priced) + (shipping share, however costed) must equal the purchase header's Total Amount Paid, to the rupiah — this is the "debits = credits" equivalent for this system and should be enforced as a hard invariant before a purchase is considered postable, not just a UI nicety.
- **SKU generation convention**: `{CATEGORY_PREFIX}-{first 1–2 words of item name, slugified}-{4-digit sequence}` (TCG/WATCH/AUTO/TOY/OTH), sequence scoped to the prefix+slug combination. Placeholder pending real user confirmation, not a settled rule.
- **Serial ID generation convention**: `{SKU}-{3-digit sequence}`, continuing from the count of existing units of that SKU. Placeholder, not settled.
- **Uniqueness is a real invariant, not just a generation-time nicety** — both SKUs and serial/asset IDs must be enforced unique at the point of commit (across all posted data, not just within one purchase), independent of whatever generated them. A real bug surfaced in the mockup where the serial-ID *generator* avoided collisions in the common case, but nothing actually blocked a save if a duplicate arose anyway (e.g. two lines of the same SKU in one purchase, or a manually-typed duplicate) — the fix was an independent uniqueness check gating save, not smarter generation alone. Milestone 2 must build the equivalent real constraint (e.g. DB unique index / explicit check), not rely on the SKU/serial generators alone to prevent collisions.
- **Invoice/proof-of-transfer upload and OCR, and per-serialized-unit photo capture, are real, confirmed near-term features** — simulated client-side only in Milestone 1 (no real Google Drive upload, no real OCR engine yet), but not speculative: Milestone 2's schema should include the nullable groundwork fields these need (an invoice/document reference, an OCR status of Parsed/Needs Review, parsed-field values, a photo reference per serial unit) so that a later ingestion milestone (real Drive upload + real OCR, mirroring Noctrowl's own Documents/invoice-capture pattern) is additive, not a schema migration. Do not build the real Drive/OCR integration itself in Milestone 2.

**Milestone 5 decision, confirmed 2026-09-10**: sale-side depletion (turning Alakazam from acquisition-only into real in/out inventory movement) uses **weighted-average cost** for fungible items — at the moment of each depletion, cost-per-unit is the average across all currently on-hand purchases of that SKU, not FIFO batch order. **Real bug found and fixed this milestone, worth remembering**: the negative-stock invariant for fungible depletion (`SELECT ... FOR UPDATE` inside an `AFTER INSERT` trigger) could **deadlock** under genuinely simultaneous concurrent depletions — not just on a real over-commit, but even between two individually valid, jointly-satisfiable requests — because Postgres's own FK enforcement already takes a `FOR KEY SHARE` lock on the referenced `items` row before the trigger runs, and two transactions' triggers both trying to upgrade that to `FOR UPDATE` forms a genuine deadlock cycle. QA caught this specifically by testing with `threading.Barrier` (true simultaneous lock acquisition) rather than event-ordered staggered timing, which is what Builder's own first-pass test used and why it initially looked clean. **Fixed structurally**, not patched: the trigger now uses `pg_advisory_xact_lock(item_id)` — a separate lock space from Postgres's FK-driven row locks, so it can never collide with the `FOR KEY SHARE` lock, and one-lock-per-transaction can't deadlock against itself by construction. A defense-in-depth layer also catches SQLSTATE `40P01` and translates it to a clean `DepletionConflictError` rather than ever surfacing a raw 500. The serialized-unit path (`deplete_serial_unit`, one atomic `UPDATE ... WHERE status = 'on_hand'`) never had this problem — relying on Postgres's own single-statement row locking, not a multi-step lock-then-check pattern, is the safer default shape for this kind of invariant. **Worth applying this lesson forward**: any future concurrency-sensitive invariant in this codebase should prefer a single atomic statement over an explicit `SELECT ... FOR UPDATE`, and any future concurrency test in this project should use `threading.Barrier` for a true simultaneity test, not just event-ordered staggering — the latter can pass cleanly while hiding a real deadlock window.

**Milestone 6 scope decisions, confirmed 2026-09-11 — grounded in real sample data, not assumption**: checked Noctrowl's real eBay Transaction Report samples (`sample-documents/eBay account 1_ricky-game/` and `.../eBay account 2_ricky-garage/`, multiple months) before designing anything, per this project's own "confirm against a real sample before building parsing logic" rule.

- **Real finding: there is no reliable machine-matchable identifier linking an eBay export row to an Alakazam item today.** eBay's own "Custom label" column (its designated spot for a seller's internal SKU) is **empty on every Order row** for the TCG/Toys account (0/392 across 4 real months). The Automotive account *does* populate it, but with values like `SCRAPED-1WD-E2450-00` / `EBAY-SOURCE-16321-74050` — **confirmed by the user (2026-09-11) to be a sourcing/vendor reference, unrelated to Alakazam item identity.** Milestone 6 must not try to interpret these as SKUs.
- **Matching approach**: a **review-queue import** — upload the CSV, the system shows each `Order` row with a fuzzy title-match suggestion against the Alakazam catalog to speed things up, but **every row requires explicit human confirmation before any depletion posts.** No row ever auto-matches and auto-posts on Custom label or title alone, even a suspiciously-exact one — same "never silently guess" discipline as Noctrowl's own bank-reconciliation review queue. This was a deliberate choice over auto-matching (even a hybrid auto-match-when-labeled option), specifically because real data shows Custom label can't be trusted as an identity signal at all today.
- **Row types**: only `Type == "Order"` rows represent actual sold inventory. `Refund`/`Hold`/`Other fee`/`Payout` rows don't move physical stock and should not deplete anything. Refund rows specifically are **not auto-reversed** in this milestone — same deliberate "no correction/reversal flow yet" gap already documented for Purchases (Milestone 2/4) and Depletions (Milestone 5); flag them for visibility, don't build reversal logic.
- **Idempotency**: re-uploading the same or an overlapping month's CSV must never double-deplete — needs a real, DB-level uniqueness constraint (not just an app-level check, per the lesson already learned twice in this project) keyed on a genuinely per-line-item-unique eBay field. Builder should verify against the real sample data which column (`Transaction ID` looked likely, `Order number` repeats across multi-item orders) is actually unique per row before committing to it.
- **Serialized items**: the CSV has no per-unit granularity, so when a matched item is serialized, the human reviewer must also pick which specific on-hand unit was sold (same manual selection already used in Milestone 5's Item Detail "Mark as Sold" flow) — the CSV only tells you *which item*, never *which unit*.
- Real column names confirmed from the actual files (note: the real CSV has a multi-line notes preamble *before* the actual header row — don't assume row 1 is the header): `Transaction creation date`, `Type`, `Order number`, `Item ID`, `Transaction ID`, `Item title`, `Custom label`, `Quantity`, plus fee/payout columns Alakazam has no use for (those are Noctrowl's concern, not inventory's).

**Milestone 6 (eBay sales ingestion) — approved 2026-09-11**, QA-signed-off on the first pass. `migrations/004_add_ebay_sales_import.sql` adds `ebay_import_batches`/`ebay_sales_rows`/`ebay_sales_row_depletions`, plus a nullable `ebay_transaction_id` column on both `fungible_depletions` and `serial_units`. `ingestion/ebay_csv.py`/`fuzzy_match.py`/`ebay_import.py` implement the real review-queue flow; `deplete_fungible`/`deplete_serial_unit` gained a new optional `ebay_transaction_id` parameter (appended last, `None` default — confirmed fully backward-compatible, every Milestone 5 call site and test unaffected). **The uniqueness key is `Transaction ID`, scoped to `WHERE row_type = 'Order'` — not globally unique.** This was a real finding from the actual data, not a design guess: a genuine case exists where a `Hold` row reuses an `Order` row's Transaction ID across different months (order `01-14825-30000`, txn `10081929607901`) — a global unique constraint would have broken on real data. `Order number` was ruled out early since it's known to repeat across multi-item orders. **Known, accepted limit of this milestone's traceability** (QA's judgment call, agreed): Hold/Other fee/Payout rows and multi-item order-summary rows are counted in the batch summary but not individually stored — reasonable, since none of them carry inventory-relevant data Alakazam doesn't already have elsewhere (Hold rows echo an already-stored Order row; Other fee/Payout carry no item reference at all and are Noctrowl's domain; order-summary rows have no Item ID/Transaction ID/title to preserve). Refund rows — the one excluded type that does carry real item data — are stored individually and fully visible, just never auto-processed (no reversal/correction flow yet, same deliberate gap as Purchases and Depletions). If per-row audit of the genuinely-irrelevant row types is ever wanted later, that's a small additive change, not a redesign.

**Real, running prototype confirmed working end-to-end, 2026-09-14**: a persistent local dev Postgres (`alakazam-dev-pg`, port 5432 — separate from the disposable `alakazam-test-pg` the test suite uses) was stood up, all 4 migrations applied, categories seeded, and the real FastAPI app started and smoke-tested (login → authenticated Inventory page/API, all 200s). Login credentials and the dev DB password are in the user's local `.env` (not committed). This is a manually-started background process on the user's machine, not a persistent/deployed service — it stops on reboot or if explicitly killed.

**Milestone 7 decisions, confirmed 2026-09-14**: pre-order/dropship is structurally inverted from everything built so far — the sale happens *before* any purchase/acquisition record exists, unlike Milestones 2/5/6 which all assume a purchase already happened. Scope for this first pass:
- **Standalone manual flow, not integrated with the Milestone 6 eBay import review queue** — recording a pre-order sale is a separate, manual action for now. Extending the eBay import to offer "record as pre-order" when a matched item has insufficient stock is an explicit future candidate, not built now.
- **Fungible items only** — serialized pre-order (no unit/serial identity exists until the item is actually acquired) is deferred; revisit only if it turns out to be a real need.
- **Many pending pre-order sales can be fulfilled by one purchase** — e.g. buying 5 units in bulk to cover 5 accumulated pending pre-orders for the same item. The purchase engine's existing multi-line/quantity support should make this natural, not a special case.
- **A still-pending (not yet fulfilled) pre-order sale can be cancelled.** This is not a correction of a posted fact — nothing has touched inventory or cost for a pending pre-order yet, so cancelling it is just discarding an unfulfilled record, not reversing a real transaction. This does not reopen the general "no correction/reversal flow" gap that still applies to already-fulfilled pre-orders, purchases, and depletions.

**Recommended design shape** (Builder's call on exact implementation, but this reuses existing engines rather than reinventing anything, consistent with this project's established discipline): fulfillment = a normal Purchase (through the existing Milestone 2 engine, unchanged) immediately followed by one `deplete_fungible()` call per pre-order sale being fulfilled (the existing Milestone 5 engine, extended with one more optional linking parameter — same pattern as Milestone 6's `ebay_transaction_id` addition) for the fulfilled quantity. This means: the purchase's cost genuinely joins the weighted-average pool before the depletion(s) draw from it (correct, not an approximation), any purchased quantity beyond what's needed for pending pre-orders correctly remains as genuine on-hand stock, and the existing negative-stock invariant automatically protects this new flow for free — no new concurrency-sensitive invariant needs inventing for the purchase+deplete half. The one new invariant genuinely needed is the pending→fulfilled/cancelled status transition itself, which must use the same safe atomic compare-and-swap pattern already proven in Milestone 5's serialized-unit path and Milestone 6's row-confirmation gate (an `UPDATE ... WHERE status = 'pending'`) — never the trigger-based `SELECT ... FOR UPDATE` pattern that caused a real deadlock in Milestone 5's original fungible design.

**Note on what this does NOT yet unlock**: Noctrowl's own real eBay sales export has no category field (confirmed in its own CLAUDE.md), so Noctrowl has no real category data of its own for this export's `category` column to actually join against yet. The Milestone 4 export is real, correct groundwork — not yet a working end-to-end reconciliation with live Noctrowl data.

**Milestone 7 (pre-order/dropship state) — approved 2026-09-14**, QA-signed-off after one fix cycle. `migrations/005_add_preorder_sales.sql` adds `preorder_sales` (item, quantity, sale_date, free-text reference, status pending/fulfilled/cancelled), backstopped by a real DB trigger enforcing fungible-only (no advisory lock needed here — `identity_mode` is write-once, so unlike Milestone 5's negative-stock trigger there's no running-total race to guard against; confirmed by grepping for any `UPDATE items SET identity_mode`, found none). `inventory/preorders.py` is the real engine: `record_preorder_sale`, `cancel_preorder_sale` (atomic `UPDATE ... WHERE status = 'pending'` compare-and-swap, never a trigger-based lock), and `fulfill_preorder_sales` (the unmodified Milestone 2 `save_purchase()` immediately followed by one `deplete_fungible()` call per pre-order being fulfilled — `deplete_fungible` gained one more optional, backward-compatible `preorder_sale_id` parameter, same pattern as Milestone 6's `ebay_transaction_id`). QA hand-verified the core correctness claim: fulfilling a pre-order against an item with pre-existing on-hand stock at a different cost produces a weighted-average depletion cost that genuinely blends both (10 units @ Rp 10,000 + 6 units @ Rp 20,000 fulfilling purchase → Rp 13,750/unit, not just the new purchase's isolated price). Bulk fulfillment (many pending pre-orders, one purchase) produces independent, correctly-computed depletions per pre-order, and a failed bulk fulfillment leaves zero trace anywhere (verified via raw SQL row counts, not just the return value).

**Real bug found this milestone — in Milestone 2's engine, not Milestone 7's own code, newly exposed as a realistic risk by Milestone 7's fulfillment flow.** `inventory/purchases.py::_generate_purchase_ref()` (unchanged since Milestone 2) has no locking/retry — two genuinely concurrent `save_purchase()` calls (reachable via two staff fulfilling different pre-orders at the same moment, or just two unrelated ordinary purchases) could both compute the same "next" ref and race on the insert, with the loser's `IntegrityError` escaping uncaught (would surface as a raw 500 through the web API). Data itself stayed correct in every trial (the unique constraint held, no duplicate ref ever persisted) — this was a failure-mode/UX bug, not data corruption, but the same class of issue already fixed twice before in this project. **Fixed with a bounded retry loop** (5 attempts, each in its own savepoint, regenerating the ref on a `purchases_purchase_ref_key` violation specifically — any other `IntegrityError` still propagates as itself, verified with a real duplicate-SKU-inside-a-new-purchase case), not an advisory lock — deliberately, because `pg_advisory_xact_lock` only releases at the outer transaction's commit/rollback, not a savepoint boundary, so it would have serialized every concurrent purchase save project-wide for unrelated items too, not just actual collisions. QA independently confirmed this reasoning is correct Postgres behavior. New `PurchaseRefConflictError` exception if retries are ever exhausted (should be effectively unreachable in practice). **This pattern — a bounded, savepoint-scoped retry keyed on a specific constraint-name check, preferred over a lock whenever the lock's blast radius would exceed the actual collision — is worth applying to any future similarly-shaped generation+insert race found in this codebase.**

**Milestone 8 decisions, confirmed 2026-09-15**: consignment — items owned by a third-party consignor, physically held by the seller, never the seller's own asset. Alakazam is explicitly the system Noctrowl expects to hold consignor-level detail (Noctrowl deliberately keeps only one aggregate "Consignor Payable" liability, per its own CLAUDE.md, and defers per-consignor tracking to "a separate system... very plausibly this one").

- **Item separation**: a consigned item always gets its own distinct item/SKU — never the same catalog entry as owned stock of a nominally-similar product. SKU uses the `CONSIGN-` prefix convention already established on Noctrowl's side for eBay listings (Noctrowl detects consignment sales by this exact prefix on the eBay listing's own SKU/custom-label field), so both systems agree on what's consigned without a manual cross-reference. Exact internal convention (e.g. `CONSIGN-{CATEGORY_PREFIX}-{NAME}-{SEQ}`) is Builder's call — flag it as a placeholder needing confirmation, same treatment as the original SKU/serial-ID conventions from Milestone 1.
- **Serialized only** — no fungible consignment support in this milestone. This was the user's explicit choice, not just an incremental-scope default like Milestone 7's fungible-only-for-preorder call: consignment is naturally suited to serialized tracking (often one-of-a-kind pieces), and scoping to serialized-only sidesteps the weighted-average cost-pooling concern entirely, since serialized units are never averaged — each carries its own direct cost (which for a consigned unit is genuinely Rp 0, since the seller never bought it).
- **Payout amount computation stays entirely on Noctrowl's side** — same "no sale price/revenue anywhere in Alakazam" boundary already established through Milestones 5-7. Noctrowl's own payout formula depends on sale price (item price × one of two live formulas, decided manually per-sale), which Alakazam deliberately doesn't track.
- **But Alakazam DOES track a paid/unpaid reimbursement status per sold consigned item** — a real scope addition beyond pure inventory tracking, confirmed deliberately by the user. This is a status flag for visibility ("has the consignor been paid back for this specific sold item yet"), not a payout amount calculation — Alakazam still never computes or stores what's actually owed in Rupiah.

**Recommended design shape** (Builder's call on exact implementation): a new `consignors` table (name, contact info). Consigned items live in the existing `items`/`serial_units` tables (an item gets an item-level `consignor_id`, since one consigned item's units always belong to one consignor, consistent with the item-separation rule above) with `acquired_cost = 0` for every consigned unit at intake — intake is NOT a Purchase (no money changes hands, no `save_purchase()` involved) and needs its own new function. Selling a consigned unit should reuse the existing, proven `deplete_serial_unit()` (Milestone 5) for the actual inventory-movement half, wrapped in a new orchestration function that also creates a reimbursement record (defaulting to unpaid) in the same transaction — mirroring how Milestone 7's `fulfill_preorder_sales` wraps the existing engine rather than reinventing inventory movement. The reimbursement status transition (unpaid → paid) needs the same atomic `UPDATE ... WHERE status = 'unpaid'` compare-and-swap pattern already proven safe in Milestones 5-7 — never a trigger-based lock. A $0 cost figure on a sold consigned unit's depletion record is correct, not a bug — don't let Builder or QA flag it as an error.

**Explicitly out of scope for this milestone**: no eBay-import (Milestone 6) integration — recording/selling a consigned unit is a standalone manual flow for now, same precedent as Milestone 7. No payout amount computation. No fungible consignment.

**Milestone 8 (consignment tracking) — approved 2026-09-15**, QA-signed-off on the first pass. `migrations/006_add_consignment.sql` adds `consignors`, `items.consignor_id` (nullable, write-once — confirmed by grep, nothing in the codebase ever updates it or `identity_mode` after insert) with a real DB trigger enforcing consigned-implies-serialized, a second trigger enforcing that a consigned unit is never tied to a `purchase_line_item_id` and always has `acquired_cost = 0` (while a non-consigned unit always does have both), and `consignor_reimbursements` (status unpaid/paid, paid-date, free-text reference — no amount field anywhere, verified by grep). `inventory/consignment.py` is the real engine: `intake_consigned_units()` (not a Purchase — no `save_purchase()` involved, zero cost by construction) and `sell_consigned_unit()`, which does a server-side pre-check on `item.consignor_id` and then calls the real, **completely unmodified** `deplete_serial_unit()` (confirmed via `git log` — no Milestone 8 commit touches `inventory/depletions.py` at all) — a genuinely different choice than Milestones 6/7's pattern of adding an optional linking parameter, made possible because `consignor_id` is write-once so a pre-check SELECT is sufficient. `mark_reimbursement_paid()` uses the same atomic `UPDATE ... WHERE status = 'unpaid'` compare-and-swap already proven safe three times before.

**Single Mark-as-Sold entry point, not two.** The existing `/api/items/{sku}/serial-units/{serial_id}/deplete` endpoint (unchanged request shape since Milestone 5) now looks up the item server-side and routes internally — consigned items go through `sell_consigned_unit()` (creating an `unpaid` reimbursement), ordinary owned items go through the plain depletion path unchanged. QA confirmed this routing is genuinely server-side (the client-facing schema has no consignment field at all) with no way to bypass reimbursement creation for a real consigned sale. A **Rp 0 cost on a sold consigned unit's depletion record is correct, not a bug** — don't flag it as an error in any future milestone's review.

QA independently reconstructed its own `threading.Barrier` concurrency test for the reimbursement status transition (25 trials, two threads racing to mark the same reimbursement paid at the exact same instant) — zero uncaught exceptions, exactly one winner every trial, and a full-table scan afterward found zero status/paid-field mismatches.

**With Milestone 8 signed off, the original planned Project-Alakazam milestone sequence (1 through 8) is complete.** Remaining known items are the ones already flagged as deliberately deferred throughout the project: the eBay-import review queue doesn't yet offer "record as pre-order" or "sell as consigned" as alternatives to plain depletion (Milestones 6/7/8 each explicitly deferred that integration); no live API/shared-DB link to Noctrowl exists (the Milestone 4 file-export handoff remains the only integration point, and Noctrowl has no real category data yet for that export's `category` column to actually join against); several SKU/serial-ID/CONSIGN- prefix conventions remain real placeholders never formally confirmed with the user, despite being used consistently; and the project-wide "no correction/reversal flow for a posted transaction" gap, acknowledged since Milestone 1, still applies everywhere (purchases, depletions, eBay imports, pre-order fulfillments, and now consignment reimbursements once marked paid).

**Architecture change, confirmed 2026-09-22 — Alakazam's own login gate is being removed.** A new sibling project, **Dotworks** (`/Users/sukmasilas/Projects/dotworks-main`), is now the single, shared entry point for both Project-Noctrowl and Project-Alakazam: one login at the Dotworks level, then a hub page linking out to each system. Noctrowl has already removed its own login gate for the same reason (see its own CLAUDE.md, "Login gate — superseded 2026-09-22"). Neither sibling keeps its own auth gate going forward — once a user authenticates at Dotworks and clicks "Inventory," they should land directly in Alakazam's app with no second login prompt. **No session-sharing/SSO mechanism exists or is being built** — this is a plain trusted-network model, not a token handoff, so Alakazam's side of this is purely "remove the login gate," not "integrate with Dotworks' auth."

**Real security implication, same one Noctrowl's own CLAUDE.md now documents about itself**: with no login gate and no real per-user permission system (deliberately deferred, not built on either side yet), Alakazam's web UI must be treated as **trusted-network-only** from this point forward — it must never be directly reachable from the public internet on its own. The only acceptable public entry point is Dotworks, via whatever reverse-proxy/firewall mechanism makes Dotworks the sole externally-reachable service (still being designed on Noctrowl's side, not yet shipped). **This is a hard, blocking requirement for any future deployment of Alakazam** — don't deploy it publicly-reachable ahead of that mechanism existing.

Note as of this decision: Dotworks' own CLAUDE.md, as it currently reads, still describes the *old* model ("each destination link still requires that system's own separate login... Dotworks is a landing page with links, not an identity provider") — that file hasn't caught up to this newer decision yet. That's Dotworks' own project to correct, not something to fix from here.
